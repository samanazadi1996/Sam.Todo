معماری فنی پروژه Todo

سندی برای یادگیری: ساختار، لایه‌ها، جریان درخواست، امنیت و تکنولوژی‌های به‌کاررفته

مستند بر اساس کد واقعی مخزن Sam.Todo نوشته شده است.

۱. نمای کلی

این پروژه یک REST API برای مدیریت وظایف (Todo) با احراز هویت مبتنی بر نقش است. کاربر می‌تواند ثبت‌نام کند، وارد شود، توکن بگیرد و با آن وظایف را بخواند یا بسازد. عملیات حساس‌تر مثل ویرایش، حذف و مدیریت کاربران فقط برای نقش ADMIN است.

۳. ساختار پوشه‌ها

ریشه بسته‌ها com.example.todo است و بر اساس مسئولیت تقسیم شده، نه بر اساس نوع:

src/main/java/com/example/todo/
├── TodoApplication.java          نقطه شروع برنامه
├── config/                       پیکربندی زیرساختی (امنیت، MVC، OpenAPI، seed)
├── controller/                   لایه دریافت درخواست HTTP
├── dto/                          اشیای تبادل داده بین لایه بیرونی و داخلی
├── entity/                       موجودیت‌های JPA
├── exception/                    استثناهای دامنه و مدیریت سراسری خطا
├── interceptor/                  فیلتر سطح Spring MVC
├── repository/                   دسترسی به پایگاه داده
├── security/                     مؤلفه‌های اختصاصی احراز هویت
└── service/                      منطق کسب‌وکار (+ پوشه impl برای پیاده‌سازی‌ها)

src/test/java/com/example/todo/
├── TodoApplicationTests.java     تست بارگذاری context
├── RoleBasedAccessControlTest.java  تست کنترل دسترسی
└── security/JwtServiceTest.java      تست واحد JWT

الگوی service + service/impl یک قرارداد رایج در پروژه‌های سازمانی است: واسط در بسته اصلی و پیاده‌سازی در بسته impl قرار می‌گیرد تا وابستگی‌ها به سمت مجرا (client) باشد نه سمت پیاده‌سازی.

۴. معماری لایه‌ای

هر درخواست از این مسیر عبور می‌کند و هر لایه فقط یک وظیفه دارد:

لایهمسئولیتچه چیزی را نباید بداند
Controllerدریافت HTTP، اعتبارسنجی ورودی، تعیین کد وضعیت پاسخنباید منطق کسب‌وکار بنویسد، نباید مستقیم به دیتابیس دست بزند
Serviceمنطق کسب‌وکار، مدیریت تراکنش، تبدیل Entity به DTOنباید از کلاس‌های HTTP مثل HttpServletRequest استفاده کند
Repositoryاجرای کوئری و کار با پایگاه دادهنباید منطق کسب‌وکار داشته باشد
Entityنگاشت جدول پایگاه داده به شیءنباید در پاسخ HTTP مستقیم برگردد
DTOشکل داده در مرز سیستمنباید منطق داشته باشد
securityاحراز هویت و ساخت توکننباید منطق دامنه را در خود داشته باشد
چرا DTO جدا از Entity؟ اگر Entity را مستقیم در پاسخ برگردانید، همه ستون‌ها (از جمله password) به کاربر نشت می‌کند. همچنین ساختار جدول پایگاه داده به قرارداد API گره می‌خورد و تغییر آن به شکست کلاینت‌ها منجر می‌شود.

۶. لایه Entity

۶.۱ موجودیت TodoItem

نگاشت یک جدول ساده به یک کلاس جاوا با annotation:

@Entity
@Table(name = "todo_items")
public class TodoItem {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 255, columnDefinition = "nvarchar(255)")
    private String title;

    @Column(nullable = false, updatable = false)
    private LocalDateTime createdAt;

    @PrePersist
    protected void onCreate() {
        createdAt = LocalDateTime.now();
    }
    // getter / setter
}
Annotationمعنا
@Entityاین کلاس یک موجودیت JPA است و به جدول نگاشت می‌شود
@Tableنام جدول در پایگاه داده
@Idکلید اصلی
@GeneratedValue(IDENTITY)کلید را خود پایگاه داده تولید می‌کند (ستون IDENTITY در SQL Server)
@Column(nullable, length, updatable)قیود ستون
columnDefinition = "nvarchar"نوع ستون دقیق؛ در SQL Server بدون این، رشته به nvarchar نگاشت می‌شود و برای متن فارسی لازم است
@PrePersistپیش از درج در پایگاه داده اجرا می‌شود — روش استاندارد مقداردهی اولیه

۶.۲ موجودیت AppUser و نقش‌ها

نقش‌ها به‌صورت مجموعه‌ای جدا در جدول دیگری نگهداری می‌شوند:

@ElementCollection(fetch = FetchType.EAGER)
@CollectionTable(name = "app_user_roles", joinColumns = @JoinColumn(name = "user_id"))
@Column(name = "role", length = 20, columnDefinition = "nvarchar(20)")
@Enumerated(EnumType.STRING)
private Set<Role> roles = EnumSet.noneOf(Role.class);
  • @ElementCollection یک مجموعه ساده را در جدول جدا ذخیره می‌کند (نه یک موجودیت مستقل).
  • FetchType.EAGER یعنی نقش‌ها همیشه همراه کاربر خوانده می‌شوند. برای کنترل دسترسی لازم است، چون در هر درخواست به نقش‌ها نیاز داریم. اگر LAZY بود، در حلقه ساخت UserDetails به مشکل LazyInitializationException می‌خوردیم.
  • EnumType.STRING مقدار enum را به‌صورت متن ذخیره می‌کند نه عدد. خواناتر است و در برابر جابه‌جایی مقادیر enum مقاوم‌تر.
  • EnumSet.noneOf(Role.class) مجموعه‌ای بهینه مخصوص enum است که در واقع یک long است — سریع‌تر از HashSet.

enum نقش‌ها با یک متد کمکی نوشته شده تا پیشوند ROLE_ در یک جا باشد:

public enum Role {
    USER, ADMIN;

    public String getAuthority() {
        return "ROLE_" + name();
    }
}
پیشوند ROLE_ تصمیم خود Spring Security است: متدهای hasRole("ADMIN") خودکار دنبال ROLE_ADMIN می‌گردند، در حالی که hasAuthority("ROLE_ADMIN") مقدار دقیق را می‌خواهد. نباید پیشوند را دوباره داخل مقدار بنویسید، وگرنه مثلاً ROLE_ROLE_ADMIN می‌شود.

۷. لایه Repository

Repository یک interface است که هیچ پیاده‌سازی ندارد. Spring Data در زمان اجرا پیاده‌سازی را می‌سازد:

@Repository
public interface TodoItemRepository extends JpaRepository<TodoItem, Long> {

    @Query("SELECT t FROM TodoItem t WHERE (:completed IS NULL OR t.completed = :completed) AND (:title IS NULL OR t.title LIKE %:title%)")
    List<TodoItem> findByFilters(@Param("completed") Boolean completed, @Param("title") String title);
}
  • extends JpaRepository<TodoItem, Long> عملیات استاندارد CRUD را به ارث می‌برد.
  • نام‌گذاری توافقی (findByUsername، existsByUsername) باعث می‌شود Spring Data کوئری را بسازد؛ نیازی به نوشتن دستی نیست.
  • کوئری بالا از نوع JPQL است — روی نام فیلدهای جاوا نوشته می‌شود نه نام ستون‌ها، و JPQL خودش به SQL تبدیل می‌شود.
  • الگوی :param IS NULL OR ... برای فیلتر اختیاری استفاده شده: اگر پارامتر null باشد شرط بی‌اثر می‌شود و آن فیلتر اعمال نمی‌گردد.
  • خروجی Optional<T> برمی‌گرداند چون ممکن است چیزی پیدا نشود — اجبار کاربر به بررسی وجود دارد.

۸. لایه Service

منطق کسب‌وکار اینجاست و تراکنش مدیریت می‌شود:

@Override
@Transactional
public TodoResponse create(TodoCreateRequest request) {
    TodoItem item = new TodoItem();
    item.setTitle(request.getTitle());
    item.setDescription(request.getDescription());
    item.setCompleted(request.getCompleted());
    return new TodoResponse(repository.save(item));
}

@Override
@Transactional(readOnly = true)
public TodoResponse getById(Long id) {
    TodoItem item = repository.findById(id)
            .orElseThrow(() -> new ResourceNotFoundException("Todo با شناسه " + id + " یافت نشد"));
    return new TodoResponse(item);
}
مفهومتوضیح
@Transactionalهمه عملیات یا با هم موفق شوند یا همه برگشت (Atomic). بدون آن، نوشتن در دیتابیس بلافاصله commit می‌شود.
readOnly = trueفقط خواندن است؛ Hibernate دستور update نمی‌سازد و می‌تواند از کش استفاده کند. برای متدهای خواندنی بهینه‌سازی واقعی است.
orElseThrowبه‌جای برگرداندن Optional خالی، استثنا پرتاب می‌کند؛ نتیجه تمیزتر برای لایه بالاتر.

در لایه Service کلاس DTO از Entity ساخته می‌شود. این تبدیل دستی عمداً انجام شده تا کنترل شود چه چیزی به بیرون می‌رود.

نکته زبان جاوا در این فایل: استفاده از var دیده نمی‌شود چون در کد از نوع صریح استفاده شده — این برای API عمومی بهتر است. همچنین عبارت‌های لامبدا در متدهایی مثل getAll برای نگاشت لیست استفاده شده‌اند:

return repository.findByFilters(completed, title).stream()
        .map(TodoResponse::new)
        .toList();

TodoResponse::new ارجاع متد (method reference) است — شکل فشرده item -> new TodoResponse(item).

۹. لایه Controller

@RestController
@RequestMapping("/api/todos")
@SecurityRequirement(name = OpenApiConfig.BEARER_SCHEME)
@Tag(name = "Todo", description = "مدیریت وظایف (CRUD)")
public class TodoController {

    @PostMapping
    @Operation(summary = "ایجاد وظیفه جدید")
    public ResponseEntity<TodoResponse> create(@Valid @RequestBody TodoCreateRequest request) {
        return ResponseEntity.status(HttpStatus.CREATED).body(todoItemService.create(request));
    }

    @GetMapping
    public ResponseEntity<List<TodoResponse>> getAll(
            @RequestParam(required = false) Boolean completed,
            @RequestParam(required = false) String title) {
        return ResponseEntity.ok(todoItemService.getAll(completed, title));
    }
}
Annotationمعنا
@RestControllerمعادل @Controller + @ResponseBody؛ خروجی به‌جای نام View، مستقیم JSON می‌شود
@Validاعتبارسنجی ورودی را فعال می‌کند؛ در صورت نقض، خطا به GlobalExceptionHandler می‌رود
@RequestBodyبدنه درخواست را به شیء تبدیل می‌کند (با Jackson)
@RequestParam(required=false)پارامتر پرس‌وجوی اختیاری
ResponseEntityکنترل دقیق کد وضعیت، هدر و بدنه پاسخ
@PreAuthorizeکنترل دسترسی در سطح متد — برای عملیات حساس
@SecurityRequirementفقط برای مستند Swagger؛ هیچ اثر امنیتی ندارد

برای خواندن کاربر جاری از @AuthenticationPrincipal استفاده شده که به‌جای دسترسی دستی به SecurityContextHolder، شیء کاربر را مستقیم تزریق می‌کند:

public ResponseEntity<UserResponse> me(@AuthenticationPrincipal UserDetails currentUser) {
    return ResponseEntity.ok(authService.getProfile(currentUser.getUsername()));
}

۱۰. لایه DTO

DTO یعنی شیء ساده انتقال داده. کلاس‌های این پروژه با getter/setter دستی نوشته شده‌اند و پیام‌های اعتبارسنجی فارسی دارند:

public class TodoCreateRequest {

    @NotBlank(message = "عنوان نمی‌تواند خالی باشد")
    @Size(max = 255, message = "عنوان حداکثر ۲۵۵ کاراکتر باشد")
    private String title;

    @Size(max = 2000, message = "توضیحات حداکثر ۲۰۰۰ کاراکتر باشد")
    private String description;
}
  • @NotBlank هم null و هم رشته خالی و هم فقط فاصله را رد می‌کند.
  • @Size محدودیت طول رشته.
  • @NotEmpty (در RoleUpdateRequest) مجموعه خالی را رد می‌کند.

کلاس پاسخ یک سازنده از روی Entity دارد تا تبدیل در یک خط انجام شود:

public TodoResponse(TodoItem item) {
    this.id = item.getId();
    this.title = item.getTitle();
    // ...
}

۱۱. مدیریت خطا

یک کلاس مرکزی همه خطاها را به JSON یکدست تبدیل می‌کند:

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<Map<String, Object>> handleNotFound(ResourceNotFoundException ex) {
        return build(HttpStatus.NOT_FOUND, "NOT_FOUND", ex.getMessage());
    }

    @ExceptionHandler({BadCredentialsException.class, UsernameNotFoundException.class})
    public ResponseEntity<Map<String, Object>> handleBadCredentials(RuntimeException ex) {
        return build(HttpStatus.UNAUTHORIZED, "BAD_CREDENTIALS", "نام کاربری یا رمز عبور نادرست است");
    }
}
خطاکدerrorزمان رخ دادن
ResourceNotFoundException404NOT_FOUNDمنبع درخواستی وجود ندارد
MethodArgumentNotValidException400VALIDATION_FAILEDاعتبارسنجی ورودی نقض شده (به‌همراه جزئیات هر فیلد)
UsernameAlreadyExistsException409USERNAME_ALREADY_EXISTSثبت‌نام با نام کاربری تکراری
BadCredentialsException401BAD_CREDENTIALSنام کاربری یا رمز نادرست
DisabledException403ACCOUNT_DISABLEDحساب غیرفعال است
AccessDeniedException403FORBIDDENکاربر وارد شده اما نقش لازم را ندارد
دو handler اختصاصی401 / 403UNAUTHORIZED / FORBIDDENپاسخ‌های خود Spring Security (پیش از رسیدن به کنترلر)
تفکیک ۴۰۱ و ۴۰۳ مهم است: ۴۰۱ یعنی «نمی‌دانم شما کی هستید» و ۴۰۳ یعنی «می‌دانم، اما اجازه ندارید». پیام‌های ورود نادرست به‌عمد یکسان‌اند تا مهاجم نتواند تشخیص دهد کدام‌یک اشتباه بوده است.

۱۲. امنیت و احراز هویت

۱۲.۱ کلاس SecurityConfig

قلب پیکربندی امنیت، متد securityFilterChain است:

http
    .csrf(AbstractHttpConfigurer::disable)
    .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
    .exceptionHandling(handling -> handling
            .authenticationEntryPoint(authenticationEntryPoint)
            .accessDeniedHandler(accessDeniedHandler))
    .authorizeHttpRequests(requests -> requests
            .requestMatchers("/api/auth/login", "/api/auth/register").permitAll()
            .requestMatchers("/v3/api-docs/**", "/swagger-ui/**", "/swagger-ui.html").permitAll()
            .requestMatchers("/api/users/**").hasRole("ADMIN")
            .anyRequest().authenticated())
    .logout(AbstractHttpConfigurer::disable)
    .addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class);
تنظیمچرا لازم است
csrf disabledتوکن در هدر ارسال می‌شود، نه کوکی — پس حمله CSRF معنا ندارد. غیرفعال کردن آن برای API بی‌حالت لازم است وگرنه هر درخواست به توکن CSRF نیاز دارد.
STATELESSهیچ نشستی (session) ساخته نمی‌شود؛ وضعیت فقط در خود توکن است.
addFilterBeforeفیلتر JWT قبل از فیلتر ورود نام کاربری/رمز اجرا می‌شود تا قبل از بررسی مجوز، کاربر شناسایی شده باشد.
logout disabledخروج از سیستم در حالت بی‌حالت بی‌معنی است؛ توکن تا انقضا معتبر می‌ماند.
@EnableMethodSecurityبرای فعال شدن @PreAuthorize لازم است.

دو bean دیگر هم تعریف شده‌اند:

  • PasswordEncoder از نوع BCryptPasswordEncoder. رمزها با الگوریتم bcrypt هش می‌شوند که برای رمز عبور طراحی شده (کند و نمک‌دار)، برخلاف SHA-256 که برای داده‌های سریع مناسب است و در برابر حمله جستجوی فراگیر آسیب‌پذیر است.
  • AuthenticationManager که در متد login استفاده می‌شود تا بررسی نام کاربری و رمز با همان زیرساخت استاندارد Spring Security انجام شود.

۱۲.۲ فیلتر خودکار (نکته ظریف)

چون JwtAuthenticationFilter یک bean از نوع Filter است، Spring Boot آن را به‌صورت خودکار به‌عنوان servlet filter هم ثبت می‌کرد — یعنی دو بار اجرا می‌شد. با این bean ثبت خودکار غیرفعال شد:

@Bean
public FilterRegistrationBean<JwtAuthenticationFilter> jwtAuthenticationFilterRegistration(
        JwtAuthenticationFilter jwtAuthenticationFilter) {
    FilterRegistrationBean<JwtAuthenticationFilter> registration =
            new FilterRegistrationBean<>(jwtAuthenticationFilter);
    registration.setEnabled(false);
    return registration;
}

۱۲.۳ خواندن هدر Authorization

private String resolveToken(HttpServletRequest request) {
    String header = request.getHeader("Authorization");
    if (header == null) return null;

    String token = header.trim();
    while (hasBearerScheme(token)) {
        token = token.substring(BEARER_SCHEME.length()).trim();
    }
    return isJwsShaped(token) ? token : null;
}
  • طرح احراز هویت بدون حساسیت به بزرگی/کوچکی حروف مقایسه می‌شود (طبق RFC 7235)؛ پس bearer و BEARER هم پذیرفته می‌شوند.
  • پیشوند تکراری حذف می‌شود، چون در Swagger UI کاربران اغلب کل مقدار شامل طرح را داخل کادر Authorize می‌چسبانند و نتیجه Bearer Bearer <token> می‌شود.
  • توکن خام بدون طرح هم پذیرفته می‌شود، چون هدر زیادی دستی پر می‌شود.
  • تنها مقادیری که شکل یک JWS دارند (سه بخش جداشده با نقطه، هر سه غیرخالی) توکن شمرده می‌شوند؛ بقیه نادیده گرفته می‌شوند تا درخواست با ۴۰۱ رد شود.
این بخش عمداً سخاوتمندانه است. از نظر امنیتی چیزی از دست نمی‌رود، چون برای عبور همچنان باید توکن با کلید درست امضا شده باشد؛ اما اگر روزی خواستید سخت‌گیر باشید، شرط hasBearerScheme را اجباری کنید تا فقط طرح Bearer پذیرفته شود.

۱۳. JWT چطور کار می‌کند

JWT یک رشته متنی با سه بخش جداشده با نقطه است: header.payload.signature

public String generateToken(AppUser user) {
    Instant now = Instant.now();
    return Jwts.builder()
            .subject(user.getUsername())
            .claim(ROLES_CLAIM, user.getRoles().stream().map(Enum::name).sorted().toList())
            .issuedAt(Date.from(now))
            .expiration(Date.from(now.plusMillis(expirationMillis)))
            .signWith(signingKey)
            .compact();
}
claimمعنا
subنام کاربری (موضوع توکن)
iatزمان صدور
expزمان انقضا — پس از آن توکن نامعتبر است
rolesفهرست نقش‌های کاربر به‌صورت آرایه‌ای از رشته‌ها

امضا با کلید متقارن HS256 ساخته می‌شود. یعنی همان کلید هم برای تولید امضا و هم برای تأیید آن استفاده می‌شود؛ پس افشای کلید یعنی امکان جعل توکن. کلید به‌صورت Base64 در app.jwt.secret است و JJWT در صورت کوتاه بودن، خطا می‌دهد تا کلید ضعیف به‌طور ناخواسته پذیرفته نشود.

نکته امنیتی: نقش‌ها داخل توکن فقط برای اطلاع‌رسانی‌اند. کنترل دسترسی واقعی در CustomUserDetailsService دوباره از پایگاه داده خوانده می‌شود. این کار عمدی است: اگر نقش کسی تغییر کند، توکن قدیمی او بلافاصله بی‌اثر می‌شود، بدون آنکه منتظر انقضای توکن بمانیم.

کلاس JwtService parser را یک بار در سازنده می‌سازد (thread-safe و کارا) و اعتبارسنجی را در یک متد متمرکز کرده است:

public boolean isValid(String token, String username) {
    try {
        Claims claims = parseClaims(token);
        return username.equals(claims.getSubject()) && claims.getExpiration().after(new Date());
    } catch (JwtException | IllegalArgumentException ex) {
        return false;
    }
}

۱۴. زنجیره فیلترها

درخواست با یک توکن معتبر چه مسیری را طی می‌کند:

String token = resolveToken(request);
if (token != null && SecurityContextHolder.getContext().getAuthentication() == null) {
    authenticate(request, token);
}
filterChain.doFilter(request, response);
  1. اگر هدر توکن نداشت، فیلتر کاری نمی‌کند و زنجیره ادامه می‌یابد.
  2. اگر از قبل احراز هویتی انجام شده باشد، دوباره کاری نمی‌کند.
  3. توکن بررسی می‌شود؛ در صورت معتبر بودن، کاربر از پایگاه داده بارگذاری و یک شیء Authentication در SecurityContextHolder قرار می‌گیرد.
  4. در صورت نامعتبر بودن، علت رد شدن در سطح debug ثبت می‌شود و زمینه امنیتی پاک می‌گردد.

نکته مهم: فیلتر هرگز خودش خطا برنمی‌گرداند. کار آن فقط «احراز هویت یا عدم احراز هویت» است؛ تصمیم‌گیری درباره مجاز بودن یا نبودن با فیلتر مجوز است.

۱۵.۱ حساب مدیر اولیه

چون اولین کاربر ثبت‌نام‌شده فقط نقش USER می‌گیرد، بدون راه‌اندازی مدیر مسیر /api/users غیرقابل دسترس می‌ماند. کلاس AdminBootstrap این مشکل را حل می‌کند:

if (!StringUtils.hasText(adminUsername) || !StringUtils.hasText(adminPassword)) {
    log.warn("حساب مدیر ساخته نشد؛ ...");
    return;
}
if (repository.existsByUsername(adminUsername)) {
    log.info("کاربر '{}' از قبل وجود دارد؛ ساخت حساب مدیر رد شد", adminUsername);
    return;
}
// ساخت کاربر با نقش‌های USER و ADMIN

این کلاس ApplicationRunner است و پس از آماده شدن کامل context اجرا می‌شود. رفتار آن idempotent است: اگر کاربر از قبل وجود داشته باشد کاری نمی‌کند، پس هر بار راه‌اندازی مجدد اپلیکیشن مشکلی ایجاد نمی‌کند.

این الگو در محیط واقعی یک تصمیم معماری است: اگر مدیر را در خود کد ایجاد کنید، حذف آن از پایگاه داده فقط تا راه‌اندازی بعدی دوام می‌آورد. در سامانه واقعی بهتر است مدیر از مسیر مدیریتی یا migration ساخته شود، و این seed فقط برای توسعه بماند.

۱۶. Filter در برابر Interceptor

این پروژه هر دو را دارد و تفاوتشان مهم است:

ویژگیFilterHandlerInterceptor
لایهServlet (پایین‌تر از Spring)Spring MVC (بالاتر از Controller)
زمان اجراقبل از ورود به DispatcherServletپس از رسیدن به handler مشخص
مناسب برایاحراز هویت، CORS، فیلتر پاسخ‌های حساسلاگ درخواست، اندازه‌گیری، پرشدن ThreadLocal

RequestInterceptor فقط در preHandle مسیر درخواست را لاگ می‌کند و WebConfig آن را روی مسیرهای /api/** ثبت می‌کند. دلیل اینکه احراز هویت در Interceptor نیست و در Filter است، این است که احراز هویت باید پیش از ورود به لایه MVC انجام شود تا همه مسیرها — از جمله مسیرهایی که اصلاً handler ندارند — محافظت شوند.

@SecurityRequirement هیچ اثر امنیتی ندارد و فقط به مستندسازی مربوط است. کنترل واقعی دسترسی از SecurityConfig می‌آید. اگر این annotation را حذف کنید، برنامه همچنان درست کار می‌کند اما در Swagger دیگر دکمه قفل نمایش داده نمی‌شود. به همین دلیل نام طرح به‌صورت ثابت public static final String BEARER_SCHEME تعریف شده تا کنترلرها به آن ارجاع دهند و رشته "bearerAuth" در چند نقطه تکرار نشود.

۱۸. دیتابیس

نگاشت‌های JPA به این جدول‌ها ترجمه می‌شوند:

spring.jpa.hibernate.ddl-auto=update در محیط توسعه راحت است اما برای تولید خطرناک: تغییر ستون یا حذف آن را خودکار انجام می‌دهد و تاریخچه‌ای نگه نمی‌دارد. برای تولید از ابزار مهاجرت مانند Flyway یا Liquibase استفاده کنید.

پارامترهای encrypt=true و trustServerCertificate=true در JDBC URL به mssql-jdbc مربوط‌اند. دومی گواهی سرور را بررسی نمی‌کند و برای توسعه لازم است، ولی در محیط واقعی یک ریسک امنیتی است که باید با یک گواهی معتبر جایگزین شود.

پوشه native/ در ریشه پروژه، یک DLL ویندوزی برای احراز هویت یکپارچه SQL Server (mssql-jdbc_auth) است که در pom.xml با -Djava.library.path ارجاع داده شده. این برنامه با احراز هویت SQL (نام کاربری و رمز) کار می‌کند، پس به آن DLL نیازی ندارد و در ایمیج Docker نیز عمداً کپی نمی‌شود.

بدون توکن تازه‌سازیبا انقضای توکن کاربر باید دوباره وارد شود. در سامانه واقعی معمولاً access token کوتاه‌عمر و refresh token بلندعمر اضافه می‌شود.
بدون محدودیت نرخروی /api/auth/login محدودیت تلاش وجود ندارد، پس در برابر حمله جستجوی رمز آسیب‌پذیر است.
بدون CORSعمداً تنظیم نشده چون پروژه فرانت‌اند ندارد. اگر بعداً فرانت‌اند اضافه شود باید تنظیم شود، وگرنه درخواست‌های مرورگر بلاک می‌شوند.
خروج از سیستمدر حالت بی‌حالت، حذف توکن از سمت سرور ممکن نیست. برای ابطال فوری باید فهرست سیاه توکن یا نسخه‌دار کردن توکن اضافه شود.
